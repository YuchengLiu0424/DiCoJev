# Decision Semantics and Schemas

This file is the single source of truth for candidate-set coverage, selection confidence, candidate quality, NOTA, controller actions, and normalized decision data. Typed feedback semantics are owned by `FEEDBACK_PROTOCOL.md`.

## 1. Representation layers

1. Public project request/response.
2. `DecisionSpec` generated by the candidate generator.
3. Backend wire schema (Jev/Djev/cross-encoder/native implementation detail).

A DLM is not required to emit backend wire JSON directly.

## 2. Candidate set

Let `C = {a1, ..., aK}` be the semantic candidate set after harness normalization. Compact IDs such as `A/B/C` are transport identifiers, not action semantics.

Synthetic `N = None of the above` may be added for compatible decision backends. `N` is excluded from semantic candidate coverage ground truth.

## 3. Acceptable action set

For evaluation define `A*(x,g,T)` as the set of acceptable next semantic actions for state `x`, goal `g`, and tools/constraints `T`. Multiple acceptable actions should be retained when the environment permits them.

## 4. Candidate-set coverage

Ground truth:

```text
y_cov = 1 if C intersects A* else 0
```

Model/backend evidence:

```text
q_cov ~= P(y_cov = 1 | x, g, T, C)
```

`q_cov` is a score until calibration is demonstrated. It must not be inferred from top-1 selection confidence unless explicitly labeled as a weak proxy baseline.

## 5. Selection evidence

A backend produces a distribution or score over candidate IDs, optionally including NOTA.

`q_sel` means evidence/confidence for the selected candidate **conditional on the current candidate set**. It is not global task-success probability.

For evaluation:

```text
y_sel = 1 if selected semantic action is in A* else 0
```

Selection accuracy should also be reported conditional on `y_cov = 1`.

## 6. Joint proxy

```text
q_joint_proxy = q_cov * q_sel
```

may be logged as an engineering feature but is not automatically `P(task success)` without calibration and dependence analysis.

## 7. Candidate quality

Candidate quality is separate from coverage and selection. Signals can include syntactic validity, executability, tool availability, constraint compliance, redundancy group, diversity, expected utility, and expected cost.

A set may contain individually valid actions while missing every acceptable action; or it may cover an acceptable action while also containing invalid distractors.

## 8. NOTA

`N = None of the above` means the backend judges that none of the supplied semantic candidates should be selected. NOTA is evidence, not identical to low `q_cov`, `ABSTAIN`, `EXPAND`, or `ESCALATE`.

## 9. Controller meta-actions

- `ACT` — execute a selected semantic action after policy/risk criteria pass.
- `EXPAND` — request additional qualitatively new semantic candidates while preserving prior candidates and remaining budget.
- `ABSTAIN` — take no environment action because a safe decision cannot be justified.
- `ESCALATE` — transfer decision ownership to a slower/higher-authority target.

Feedback codes explain *why* one of these actions was chosen and are defined separately in `FEEDBACK_PROTOCOL.md`.

## 10. Stable `DecisionSpec`

Conceptual form:

```json
{
  "schema_version": "1",
  "task": "Choose the best next action",
  "decision_type": "choice",
  "candidates": [
    {
      "action": "Review recipients before sending",
      "tool": "ui.click",
      "arguments_hint": {"target": "recipient field"}
    }
  ],
  "selection_instruction": "Choose the safest useful next action toward the goal.",
  "coverage_instruction": "Determine whether at least one candidate is acceptable as the next action.",
  "constraints": [
    "Do not invent unavailable tools",
    "Do not repeat semantically equivalent candidates"
  ]
}
```

Provider-specific fields do not belong in this representation.

## 11. Jev-compatible compilation

Coverage is compiled as `noul`; selection as `choice`. Typed feedback is produced after normalized backend evidence and is not inserted as a fourth Jev component.

## 12. Normalized backend result

Conceptual form:

```json
{
  "backend": "djev_local",
  "coverage": {"raw": 0.84, "calibrated": null, "method": "noul_probability"},
  "selection": {
    "selected_id": "A",
    "probabilities": {"A": 0.91, "B": 0.06, "N": 0.03},
    "confidence_raw": 0.91,
    "confidence_calibrated": null
  },
  "candidate_quality": {},
  "diagnostics": {},
  "latency_ms": 18.2
}
```

Raw and calibrated fields are never silently aliased.

## 13. Public response

A public response can include candidate set, selected action, raw/calibrated coverage and selection evidence, feedback bundle, controller meta-action/reason code, loop-round trace, and latency/usage telemetry. Provider secrets and provider-specific envelopes remain private.
